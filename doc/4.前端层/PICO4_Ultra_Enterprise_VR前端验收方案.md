# PICO 4 Ultra Enterprise VR 前端验收方案

> 项目：CathSim 医疗导管/导丝导航与强化学习仿真平台
>
> 目标设备：PICO 4 Ultra Enterprise
>
> 验收对象：Godot 4.7.1 Android OpenXR 客户端及其桌面共享核心
>
> 依据：`PICO4_Ultra_Enterprise_VR前端设计方案.md` v2.0、`PICO4_Ultra_Enterprise_VR前端开发规划.md` v2.0
>
> 方案版本：v2.0
>
> 更新日期：2026-08-03

---

## 1. 目的

本方案用于验证 PICO 4 Ultra Enterprise VR 前端是否达到第一版发布要求，并为验收人员提供统一的环境、步骤、预期结果、证据和判定规则。

验收不以“代码已提交”“编辑器可以运行”或“已有演示截图”作为完成依据。第一版必须在目标 PICO 真机、正式候选 APK、约定后端和约定病例上完成端到端验证。

核心判定目标：

1. Android OpenXR 应用可安装、启动、退出和恢复；
2. 头部与双手柄追踪可靠；
3. VR 与桌面显示同一后端权威导航状态；
4. Deadman 连续控制有效；
5. 所有失效路径均在同一客户端更新周期（通常为 XR 帧）归零；
6. 急停请求、后端锁存、拒绝和恢复形成闭环；
7. 常驻安全状态清晰、真实且不只依赖颜色；
8. VR Balanced 满足冻结后的性能基线；
9. 空间布局和观察模式满足坐姿舒适性；
10. 签名 APK、配置、部署和桌面回归证据完整。

本验收仅证明科研仿真和教学场景下的软件质量，不构成真实临床控制、医疗器械认证或硬件急停认证。

## 8. 证据与结果记录规则

### 8.1 单个用例证据

每个用例至少记录：

- 用例 ID 和版本；
- 执行日期、执行人和复核人；
- 设备、APK、后端、病例版本；
- 前置条件和实际输入；
- 实际结果；
- 客户端日志范围；
- 后端日志范围；
- 截图或录像编号；
- 性能数据文件；
- Pass、Fail、Blocked 或 Not Run；
- 缺陷编号和严重级别。

### 8.2 “同周期归零”取证

“同周期”指失效事件被客户端 XR/输入层观察到的更新周期 `N` 内（正常运行时通常对应一个 XR 帧），`XRSafetyGate` 与 `ControlRouter` 输出已变为中性：

```text
update N:
  failure_event = true
  controls_blocked = true
  routed_push = 0
  routed_rotate = 0
  nonzero_send_allowed = false
```

验收证据必须同时包含：

1. 失效事件被观察到的更新周期/XR 帧编号；
2. SafetyGate 与 Router 在该周期输出的锁定状态和中性值；
3. 该周期以后不存在新的非零发送；
4. 后端未在事件后应用新的非零控制；
5. 若网络仍可用，客户端发送一次中性控制帧的记录。

只观察 UI 数值变成 0，或只看到后端最终归零，都不能证明客户端按要求同周期门控。

### 8.3 结果状态

| 状态 | 定义 |
|---|---|
| Pass | 实际结果完全满足预期，证据齐全 |
| Fail | 实际结果不符合预期 |
| Blocked | 环境或依赖阻止执行，不能替代 Pass |
| Not Run | 未执行 |
| Conditional | 仅用于最终总体结论，不用于单条 P0 用例 |

## 16. 性能与稳定性验收

### 16.1 测量规则

- PICO 使用参数冻结表中的设备实际目标刷新率 `F_display`；
- 使用 Release APK，不使用编辑器远程运行结果替代；
- 默认以 Compatibility/OpenGL ES 和 VR Balanced 建立发布基线；
- 测试前记录设备温度、电量和后台应用；
- 每场景预热后再采样；
- 同时采集 CPU/GPU 帧时间、平均/P95/P99、丢帧、FPS、内存、温度和热状态；
- 不用异步空间重投影掩盖持续性能不足；
- 安全状态与控制处理频率不得为换取 FPS 而降低。

## 19. 破坏性与探索性测试

在正式用例通过后执行：

- 快速连续按下/松开 Deadman；
- 两手柄交替失去追踪；
- 急停请求中断网；
- Resume 请求中断网；
- session 切换期间快速操作控制器；
- 数据在 fresh/stale 边界反复抖动；
- 高频开关面板和观察模式；
- 高复杂度病例中快速旋转头部；
- 电量低、手柄重连和应用从后台恢复；
- 配置文件缺失、格式错误或地址不可达；
- 后端返回未知字段或缺少非关键字段。

探索性测试不得绕过安全病例限制。发现的问题按同一缺陷分级规则处理。

## 20. 缺陷分级与处置

| 级别 | 定义 | 示例 | 发布规则 |
|---|---|---|---|
| P0 | 可能产生非预期非零控制、急停失效、权威状态误导、数据伪造或无法启动 | 失焦后继续控制、锁存被绕过、stale 显示安全、空风险被伪造成危险体 | 必须修复并全量复测 |
| P1 | 核心任务不可完成、关键状态不可读、持续严重掉帧 | 双手柄之一不可用、Balanced 持续低于门槛 | 必须修复或正式裁剪范围 |
| P2 | 次级功能或局部视觉问题 | 次级面板排版、非阻塞性日志问题 | 可带已知问题发布 |
| P3 | 不影响任务的优化建议 | 动画细节、调试体验优化 | 后续排期 |

缺陷修复后至少复测：

1. 原失败用例；
2. 同模块相邻用例；
3. 对应桌面或 VR 共享核心回归；
4. 涉及控制/安全时全套 SAFE 与 ESTOP P0 用例。

### 21.1 通过

- 所有准入条件完成；

- 无未关闭 P0/P1；
- 候选 APK SHA-256 与最终交付包一致；
- 版本矩阵、设计追踪和 M0–M7 门禁证据完整；
- 发布候选 30 分钟稳定性通过；
- 验收负责人和安全复核人签字。

### 21.2 有条件通过

仅允许：

- P0、P1 全部通过；
- 剩余问题均为 P2/P3；
- 不影响安全、核心任务、数据真实性和性能底线；
- 已明确限制、规避措施、责任人和关闭时间；
- 经项目负责人、验收负责人和安全复核人共同批准。

有条件通过不能用于掩盖 Blocked、Not Run 或缺少真机证据。

### 21.3 不通过

符合任一项：

- 任一 P0/P1 Fail；
- 任一 P0/P1 Blocked 或 Not Run；
- 未使用目标 PICO 真机或最终候选 APK；
- 关键参数未冻结；
- 无法证明同周期归零或急停锁存；
- 性能、舒适性或桌面回归未执行；
- 交付 APK 与验收 APK 不一致；
- 证据不完整或不可追溯。
