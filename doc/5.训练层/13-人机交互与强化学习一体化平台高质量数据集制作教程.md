# 强化学习训练教程（二）：人机交互数据收集与高质量数据集制作

> 适用对象：负责 HCI 采集、强化学习数据工程、模仿学习和评估的开发者
>
> 适用代码：`services/session_recording.py`、`services/websocket_handler.py`、`services/navigation_engine.py`、`src/cathsim/gym/envs/navigation.py`
>
> 上一篇：[12-强化学习训练教程-从环境检查到首次PPO实验.md](12-强化学习训练教程-从环境检查到首次PPO实验.md)
>
> 设计依据：[11-强化学习训练设计方案.md](11-强化学习训练设计方案.md)

本文的目标不是“尽可能多地保存帧”，而是建立一条可以回答以下问题的数据闭环：

```text
谁在什么环境中
  → 看到了什么
  → 想做什么
  → 控制器实际执行了什么
  → 物理环境发生了什么
  → 为什么结束
  → 数据经过了哪些检查和人工复核
  → 最终被分到 train / validation / test 的哪一部分
```

只有来源可追踪、动作语义正确、前后状态对齐、质量经过验证的数据，才适合用于行为克隆、恢复学习、离线分析和强化学习评估。

---

## 1. 先区分四种“数据”

### 1.1 Raw data：原始数据

原始数据是采集时服务端真实收到和产生的记录，例如：

- 人发送的 `control`；
- 点击导航发送的 `shape_intent`；
- 策略请求的 action；
- Controller 解算出的实际 `push/rotate`；
- `NavigationState`；
- Newton 参数、血管资产和 route；
- reset、人工接管、急停、碰撞与超时事件。

原始数据应尽量保持不可变。后续修正标签时新增派生版本，不直接改写原始文件。

### 1.2 Transition：一步状态转移

强化学习中最基本的数据单元是：

```text
(obs_t, requested_action_t, effective_action_t,
 reward_t, costs_t, obs_t+1, terminated_t, truncated_t)
```

这里必须同时保留：

- `requested_action`：人或策略想执行的动作；
- `effective_action`：经过限幅、ShapeIntentController 或 Safety Shield 后，物理引擎真正执行的动作。

两者不一定相同。只记录其中一个，会丢失控制器与安全层是否介入的重要信息。

### 1.3 Episode：完整回合

Episode 从一个明确的初始状态开始，到以下事件之一结束：

- 成功到达；
- 碰撞停止；
- 引擎结束；
- 超时；
- 人工急停；
- 操作者放弃；
- 系统异常；
- route 或设备配置改变，需要开启新回合。

一个文件中可以存放多个 episode，但每一步必须有明确的 `episode_id`，不能靠时间间隔猜测 reset 边界。

### 1.4 Gold data：高质量人工认可数据

Gold data 不是“成功 episode”的同义词。它至少要求：

- 数据来源和许可清楚；
- 操作者、环境、代码和配置可追踪；
- schema、数值、时序和物理检查通过；
- 动作与状态对齐；
- 关键片段经过人工或专家复核；
- 失败和恢复被正确标注；
- split 没有患者/几何泄漏；
- 已知限制写入数据卡。

Autopilot、RL 策略或脚本生成的数据可以是有价值的 synthetic/silver data，但不能因为自动检查通过就称为人工验证的 gold data。

## 2. 当前代码已经有什么

### 2.1 HCI 控制入口

Godot 当前提供三类主要控制来源：

| 来源 | 客户端行为 | 服务端入口 |
|---|---|---|
| 键盘/按钮手动控制 | 发送 `delta_push`、`delta_rotate`、`microcatheter_advance` | WebSocket `control` |
| 点击自动导航 | 发送 waypoint ShapeIntent，之后用零输入按约 20 Hz 触发步进 | WebSocket `shape_intent` + `control` |
| 后续 RL_ASSIST | 策略输出 ShapeIntent 或 direct action | 尚需完成策略在线接入与录制 |

手动输入只在有 W/S/A/D 操作时发送，客户端默认约 20 Hz，并受服务端约 30 Hz 的限流和单请求 lock-step 约束。因此 HCI 数据不能假设为固定 60 Hz。

### 2.2 可用的服务端状态

`NavigationState` 已包含：

```text
tip_position / tip_direction / tip_quaternion
velocity
contact_force / wall_distance / curvature
path_progress / path_deviation / remaining_distance
vessel_radius
fidelity_mode
risk_score / risk_assessment / risk_regions
joint_positions / joint_velocities
reward / done / safety_status
flow_guidance
```

`state_batch` 还可包含：

- 导丝 body 位姿；
- path、entry 和 target；
- backend diagnostics；
- guidewire/support/procedure/risk 信息；
- training score 与 episode 摘要。

这些字段不是都要塞进主训练张量。高频、体积大的 body 数据和静态 path 应单独存储，通过 ID 或 hash 关联。

### 2.3 现有 `SessionRecorder`

`services/session_recording.py` 当前支持：

```text
metadata
frame:
  t
  control
  state
```

并能计算：

- duration；
- steps；
- completion；
- mean/max deviation；
- max contact force；
- max risk score；
- dangerous-status frame 数量。

先运行契约测试：

```bash
cd /home/ps/cathsim-warp
PYTHONPATH=/home/ps/cathsim-warp:/home/ps/cathsim-warp/src \
  reinforcement_learning/.venv310/bin/python -m pytest -q \
  tests/test_session_recording.py
```

测试通过只能证明 JSONL 往返读取和基础评分可用。

### 2.4 必须明确的实现边界

当前录制能力仍是原型：

1. `SessionRecorder` 目前只在测试中调用，没有接入 `SessionManager` 或 WebSocket。
2. 它把 frame 全部缓存在内存中，`save()` 时用写模式生成文件；进程异常退出时可能丢失尚未保存的数据。
3. 它没有显式记录 `obs_t → obs_t+1`、ShapeIntent、实际执行动作、reward components、costs 和 termination reason。
4. 当前 `danger_events` 实际是危险状态的 frame 数，不是去重后的危险事件次数。
5. `state.reward` 来自 `NavigationEngine`，不应默认等同于 `NavigationGymEnv` 的 RL reward。
6. `src/cathsim/rl/data.py` 的 `Trajectory` 是旧数据路径，主要使用 pickle 和旧式 Gym step API，不适合作为新数据集的权威交换格式。

所以当前代码可以支持“录制原型验证”，但还不能直接宣称已经具备高质量 HCI 数据集生产线。

## 3. 为什么采集点必须放在服务端

推荐的权威采集位置是：

```text
WebSocket / policy request
        │
        ▼
输入校验与限幅
        │
        ▼
ShapeIntentController / Safety Shield
        │
        ▼
NavigationEngine.step()
        │
        ▼
Newton/Warp
        │
        ▼
NavigationState
        │
        ▼
服务端 Transition Recorder
```

客户端可以另外记录 UI 事件、点击坐标和相机画面，但训练用 transition 应以服务端记录为准，原因是服务端最接近真实执行结果。

### 3.1 点击自动导航的典型陷阱

点击导航启用后，Godot 会周期性发送：

```text
control(push=0, rotate=0)
```

但 `NavigationEngine.step()` 会在 intent 激活时用 `ShapeIntentController` 覆盖这组零输入，真正执行另一组 `push/rotate`。

如果只在 WebSocket 接收层保存客户端 control，数据会错误地显示：

```text
动作一直为零，但导丝持续前进
```

正确记录应为：

```text
requested_control = [0, 0]
active_shape_intent = {...}
effective_control = [controller_push, controller_rotate]
control_source = "click_autopilot"
```

`NavigationEngine` 已在 `_last_control_metrics` 中保留实际 push、rotate、support 和 progress delta，可作为接入录制器时的权威候选来源。

### 3.2 记录请求与执行之间的每层变化

建议把 action 分成四层：

| 层 | 示例 | 用途 |
|---|---|---|
| `ui_action` | 按键、按钮、点击 waypoint | 复现人机交互意图 |
| `requested_action` | direct control 或 policy action | 模仿学习标签和策略分析 |
| `controller_action` | ShapeIntentController 输出的 push/rotate | 分析控制抽象 |
| `effective_action` | 限幅和安全层之后送入物理引擎的动作 | 构造真实 transition |

如果 Safety Shield 没有修改动作，也应记录 `intervened=false`，而不是省略该字段。

## 4. 先定义数据用途，再开始采集

同一批数据不一定同时适合所有任务。

| 用途 | 核心标签 | 不可缺少的质量要求 |
|---|---|---|
| 行为克隆 BC | `obs_t → requested/expert_action` | 专家来源、动作语义、恢复动作、人工复核 |
| Controller 学习 | ShapeIntent、effective push/rotate | 请求与执行动作同时存在 |
| 离线 RL | obs、action、reward、cost、next_obs、done | transition 完整、reward 版本固定、覆盖失败状态 |
| Reward 调试 | reward components、状态变化 | 每一分量可重算、有公式版本 |
| 安全模型 | 接触、穿透、屈曲、shield、终止原因 | 事件定义明确、正负样本均衡 |
| 策略评估 | 完整 episode 与环境配置 | 冻结测试集、不可参与训练或调参 |
| HCI 研究 | UI 事件、接管、反应时间 | 操作者授权、时间同步、隐私控制 |

采集前填写“collection card”：

```text
collection_id:
目标任务:
允许的数据来源:
禁止的数据来源:
phantom / case / route 范围:
物理引擎与参数:
控制模式:
操作者要求:
计划 episode 数:
成功/失败/恢复目标比例:
必须记录的字段:
人工复核规则:
停止采集条件:
```

如果用途还不明确，不要先采集数十万帧再决定标签。

## 5. 推荐的数据分层

建议把数据分成四层：

```text
L0 raw events
  → L1 aligned episodes
  → L2 validated dataset
  → L3 gold / benchmark release
```

### 5.1 L0：原始事件

保存服务端真实事件，尽量少做变换：

- session start/stop；
- reset 和 route switch；
- UI/requested action；
- ShapeIntent 更新；
- engine/device 参数更新；
- effective action；
- state before/after；
- safety intervention；
-异常。

L0 只追加，不覆盖。每个 shard 完成后计算 checksum。

### 5.2 L1：对齐后的 episode

把原始事件转换为明确的 transition：

```text
step_id
obs_t
requested_action_t
effective_action_t
obs_t+1
reward_t
costs_t
terminated_t
truncated_t
termination_reason
```

这一步处理：

- reset 边界；
- 时间对齐；
- action hold duration；
- 缺失帧；
- 重复消息；
- 控制请求被限流或跳过；
- state 与 action 的因果顺序。

### 5.3 L2：验证后的数据集

通过自动质检后生成：

- 规范化数值数组；
- episode 索引表；
- 统计报告；
- reject 清单；
- review queue；
- 初步 split。

不合格数据应进入 quarantine，而不是静默删除。

### 5.4 L3：Gold 与 benchmark

L3 只包含：

- 人工复核通过的 gold demonstrations；
- 冻结的 validation/test episode；
- 明确的数据卡、许可、版本、checksum；
- 可复现的转换配置和代码 commit。

训练集、验证集和测试集应发布各自固定 manifest。测试集标签可限制访问，防止训练代码误用。

## 6. 推荐目录结构

建议在 `reinforcement_learning/data/` 下按版本组织：

```text
reinforcement_learning/data/
├── raw/
│   └── <collection_id>/
│       ├── collection.json
│       ├── events/
│       │   ├── shard-00000.jsonl
│       │   └── shard-00001.jsonl
│       ├── assets/
│       │   └── manifest.json
│       └── checksums.sha256
├── processed/
│   └── <dataset_version>/
│       ├── dataset.json
│       ├── episodes.parquet
│       ├── transitions/
│       │   └── *.zarr
│       ├── reviews.parquet
│       ├── rejects.parquet
│       ├── statistics.json
│       └── checksums.sha256
├── splits/
│   └── <dataset_version>/
│       ├── train.txt
│       ├── validation.txt
│       ├── test.txt
│       └── challenge_holdout.txt
└── reports/
    └── <dataset_version>/
        ├── quality_report.md
        └── data_card.md
```

这是建议结构，当前仓库尚未实现相应的转换命令。

### 6.1 为什么不把 pickle 作为正式交换格式

pickle 适合可信环境中的临时 Python 对象，但不适合作为长期数据集边界：

- 加载不可信 pickle 可能执行恶意代码；
- schema 不透明；
- 对类和 Python 版本耦合；
- 跨语言和审查困难。

推荐：

- JSONL：原始事件和便于审查的小规模记录；
- Parquet：episode 索引、标注和统计表；
- Zarr 或 HDF5：大规模连续数组；
- JSON：manifest、配置、数据卡和质量报告。

## 7. 推荐 schema

### 7.1 Collection metadata

每次采集必须固定：

```json
{
  "schema_version": "cathsim-transition-v1",
  "collection_id": "hci_stage0_20260724_a",
  "created_at_utc": "2026-07-24T00:00:00Z",
  "code_commit": "<git commit>",
  "collector_version": "<collector commit or package version>",
  "physics_engine": "newton",
  "fidelity_mode": "physics",
  "phantom": "aorta_tree",
  "case_id": "aorta_tree",
  "route_target": "endpoint_0",
  "asset_manifest_hash": "<sha256>",
  "engine_params": {},
  "controller_params": {},
  "reward_version": "navigation_reward_v1",
  "operator_id": "<pseudonymous id>",
  "policy_source": "human",
  "consent_or_authorization": "<record id>",
  "notes": ""
}
```

不要把操作者姓名、邮箱或其他直接身份字段写进训练数据。使用受控映射表生成匿名或假名 ID。

### 7.2 Episode metadata

每个 episode 至少记录：

```text
episode_id
collection_id
session_id_hash
case_id / route_target
split_group_id
operator_id
policy_source
control_mode
fidelity_mode
seed
started_at_utc / finished_at_utc
initial_state
engine_params / device_config
success
termination_reason
steps
duration_s
max_progress
final_progress
max_contact
contact_integral
max_risk
shield_intervention_count
review_status
raw_shard / raw_offset
```

`policy_source` 推荐取值：

```text
human
scripted_autopilot
click_autopilot
ppo
sac
human_takeover
dagger_correction
recovery_expert
random_safety_probe
```

### 7.3 Transition

建议每一步包含：

```text
episode_id / step_id
wall_time_utc_ns
monotonic_time_ns
sim_time_s
dt_s

obs
requested_action
active_shape_intent
controller_action
effective_action
action_hold_s

next_obs
engine_state
reward
reward_components
costs
shield_intervened
shield_reason

terminated
truncated
termination_reason
```

时间字段不能只保留系统墙上时间。系统时间可能被校时，应同时记录单调时钟；若 backend 提供仿真时间，再单独保存 `sim_time_s`。

### 7.4 Observation 与状态分开

建议同时保存：

- `engine_state`：完整、接近原始的 `NavigationState`；
- `obs`：由确定版本的 observation builder 生成的训练输入。

这样 observation 设计改变后，可从原始状态重新生成，而不必重新采集。

当前第一版 obs 应与 `NavigationGymEnv._state_to_obs()` 对齐：

```text
tip_position
tip_direction
target_direction_local
local_tangent
previous_action
progress
progress_velocity
contact_duration
deviation
contact_force
wall_distance
curvature
risk_score
remaining_distance
vessel_radius
```

需要保存 observation builder 的版本和归一化参数。

### 7.5 Reward 与 cost 分开

不要只存总 reward。至少保存：

```text
progress
alignment
regression
deviation
contact
risk
smoothness
terminal
timeout
```

安全 cost 单独保存：

```text
contact
penetration
buckling
wrong_branch
shield_intervention
```

HCI 状态中的 engine reward 与 RL reward 要使用不同字段名，例如：

```text
engine_reward
rl_reward
rl_reward_components
```

这样可以修改 reward 公式并离线重算，而不会污染原始记录。

## 9. 人机交互数据采集协议

### 9.1 操作者准备

每位操作者应：

- 使用假名化 `operator_id`；
- 完成相同的操作说明；
- 先做不进入数据集的 warm-up；
- 清楚成功、失败、急停和放弃的定义；
- 不在同一 episode 中私自切换 phantom、route 或物理参数；
- 知道何时标记“需要复核”。

如果记录人类表现或反应时间，应按项目的数据治理流程取得授权，并限制原始数据访问。

### 9.2 每个 episode 的流程

#### A. 开始前

确认：

```text
operator_id
case_id / route_target
control_mode
device_config
engine_params
collection_id
episode intent: normal / recovery / failure probe
```

#### B. 开始

- 创建新 session 或明确 reset；
- 保存 initial state；
- 记录 route、path hash 和 entry；
- 确认 fidelity 是 `physics`，而不是 `guided`；
- 确认 recorder 已开始写盘。

#### C. 操作中

- 不隐藏人工接管；
- 不删除误操作；
- 对犹豫、急停、撤回和恢复保留原始记录；
- 发生异常时标记事件，不要继续把多个逻辑回合混在一起。

#### D. 结束

记录唯一 termination reason：

```text
success
collision_stop
engine_done
timeout
wrong_branch
manual_abort
emergency_stop
system_error
route_changed
config_changed
```

然后立即关闭 shard 或写入可恢复 checkpoint，生成 checksum。

### 9.3 不只采集“漂亮成功”

只保存成功轨迹会造成严重分布偏差。策略看不到：

- 顶壁前兆；
- 错分支；
- 前进后回退；
- 长时间无进度；
- 扭转未传递；
- 屈曲前兆；
- 人工接管；
- 安全层干预；
- 恢复动作。

高质量示范集应包含：

```text
正常成功
低风险失败
困难但成功
错误状态恢复
策略失败后的人工纠正
安全停止
```

随机危险动作只适合安全边界覆盖或分类器负样本，不应直接混入行为克隆的专家动作标签。

## 10. Autopilot、RL 和 DAgger 数据

### 10.1 Scripted/click autopilot

Autopilot 数据适合：

- 验证环境可达性；
- 建立简单路线 silver baseline；
- 预训练 ShapeIntent 或 Controller；
- 发现系统性失败状态。

必须记录：

- intent；
- Controller 实际动作；
- autopilot/controller 版本；
- 是否发生 stall、扫掠或回拉；
- 人是否接管。

不要把 autopilot 成功轨迹标为人类专家 gold data。

### 10.2 RL policy rollout

策略 rollout 至少记录：

```text
policy_id / model checksum
algorithm
training dataset version
deterministic flag
policy action
effective action
recurrent state（若有）
observation version
```

否则无法判断两个 rollout 是否来自同一模型或同一推理设置。

### 10.3 DAgger 与人工纠正

DAgger 的核心不是只记录人最终接管后的动作，而是保存：

```text
policy_obs
policy_proposed_action
expert_corrected_action
effective_action
takeover_reason
```

推荐标注接管原因：

```text
wrong_branch
wall_contact
stall
oscillation
excessive_push
unsafe_rotation
uncertain
operator_preference
```

人工纠正样本应提高采样权重，但不能重复复制同一帧来“增加数据量”；使用显式权重更容易追踪。

## 11. 自动质量检查

### 11.1 Schema 检查

每个 episode 必须满足：

- 必填字段存在率 100%；
- schema version 已知；
- 数组 shape 和 dtype 一致；
- episode/step ID 唯一；
- source、mode、fidelity 和 route 非空；
- termination reason 属于固定枚举。

### 11.2 数值检查

要求：

- NaN/Inf 为 0；
- action 在声明范围内；
- progress 在 `[0,1]`；
- risk score 在 `[0,1]`；
- quaternion、方向向量和归一化量符合契约；
- 距离、力和曲率单位明确；
- 不把毫米当米；
- 不用静默 `clip` 掩盖大规模上游错误。

被 clip 的原始值也应保留或计数，以便发现传感器和转换问题。

### 11.3 时序与 transition 检查

要求：

- `step_id` 连续；
- 单调时间严格递增；
- `obs_t+1` 与下一条的 `obs_t` 一致或误差在允许范围内；
- reset 后历史量归零；
- episode 结束后不再追加普通 transition；
- 被限流、丢弃或超时的 action 有明确状态；
- action hold duration 可计算；
- requested 和 effective action 的差异可解释。

### 11.4 物理检查

至少检查：

- initial state 不穿壁、不含非有限数；
- 瞬时位移和速度不超过工程阈值；
- progress 大跳变需要有原因；
- contact、penetration、wall distance 的符号和单位一致；
- `guided` 数据没有混入 Newton physics 训练集；
- route、entry、target 与资产 manifest 一致；
- Safety Shield 触发后动作和终止行为符合契约。

阈值必须来自物理标定和项目验收，不应在数据教程中臆造临床安全标准。

### 11.5 重复与泄漏检查

检查：

- 完全重复 episode；
- 相同原始 episode 的重编码版本；
- 近重复动作/状态序列；
- 同一 case 的不同 route；
- 同一原始几何的平滑、镜像、缩放和随机化版本；
- 同一人工纠正片段的多次导出。

所有派生版本必须继承同一个 `split_group_id`。

## 12. 人工复核与质量分级

推荐三级：

| 等级 | 定义 | 允许用途 |
|---|---|---|
| Raw | 仅完成采集和 checksum | 调试、重处理 |
| Silver | 自动检查通过，来源清楚，但未完成专家复核 | 环境分析、预训练、候选样本 |
| Gold | 自动检查通过，关键片段人工复核，标签和限制明确 | 行为克隆主训练、基准评估 |

### 12.1 人工复核界面至少显示

- 路径和尖端运动；
- requested/effective action；
- progress、deviation；
- contact、risk、safety status；
- termination reason；
- intent/controller/shield 状态；
- episode 时间轴；
- 异常检查结果。

### 12.2 复核标签

```text
accept
accept_with_note
reject_bad_alignment
reject_wrong_action_label
reject_physics_instability
reject_missing_state
reject_wrong_route
reject_operator_error
needs_second_review
```

修改标签时记录：

```text
reviewer_id
reviewed_at
old_value
new_value
reason
source_frame
```

不要直接改写原始 event。

### 12.3 双人复核

以下数据建议至少双人复核：

- validation/test；
- 安全事件；
- 穿透、屈曲和 wrong-branch 标签；
- DAgger 纠正；
- 将被称为 gold 的恢复示范；
- 影响准入结论的 episode。

存在分歧时保留两位复核者的原始标签和最终裁决。

## 13. 数据集切分

### 13.1 先按 case/patient 分组

切分顺序必须是：

```text
原始 case / patient
  → 固定 split
  → 再生成 route、平滑、增强和随机化版本
```

不能先生成大量 route，再随机按 episode 切分。否则同一血管几何会同时出现在训练和测试中。

### 13.2 推荐 split 结构

可从以下结构起步，再按数据规模调整：

```text
train
validation
test
challenge_holdout
```

- `train`：允许用于模型训练；
- `validation`：允许用于模型选择和调参；
- `test`：只用于阶段性正式评估；
- `challenge_holdout`：长期冻结，不用于日常调参。

不要为了得到更好的图表反复查看 challenge holdout。

### 13.3 其他分组约束

除 case 外，还可能需要：

- 操作者分组：评估对未见操作者示范风格的鲁棒性；
- 时间分组：评估 UI 或设备版本变化；
- 资产来源分组：评估跨数据源泛化；
- 物理参数区间分组：评估未见参数。

训练结论必须说明测试集究竟“未见”了什么。

## 14. Dataset manifest 与数据卡

### 14.1 Dataset manifest

机器可读 manifest 至少记录：

```text
dataset_name / version
schema_version
parent_dataset
code commits
source collections
episode/transition counts
case/route/operator/source 分布
split manifests
normalization statistics
reward/observation versions
quality checks
reject counts and reasons
review coverage
licenses/authorizations
checksums
known limitations
```

### 14.2 Data card

面向人类的数据卡回答：

1. 数据用于什么？
2. 不应用于什么？
3. 谁或什么系统产生了数据？
4. 包含哪些 phantom、route、物理参数和控制模式？
5. 有多少成功、失败和恢复？
6. 哪些数据是 human、autopilot、RL、synthetic？
7. 如何质检和复核？
8. 如何切分，如何防泄漏？
9. 有哪些许可、隐私和访问限制？
10. 有哪些已知偏差？
11. 哪些安全指标尚未标定？
12. 如何复现处理流程？

“公开可见”不自动代表可重新分发。血管资产、医学影像、操作者数据和第三方模型都要分别核查许可和授权。

## 15. 第一版数据集的建议验收标准

第一版不要先追求百万帧。建议先建立一个小而完整的 dataset pilot。

### 15.1 工程验收

- 原始 shard 可在异常中断后恢复；
- checksum 覆盖率 100%；
- required field 缺失率 0；
- NaN/Inf 为 0；
- action/state 对齐错误为 0；
- unknown termination 为 0；
- 每个 episode 可追溯到 raw offset；
- 每个资产和配置有版本/hash；
- 所有 reject 都有原因；
- train/validation/test 无 `split_group_id` 交叉。

### 15.2 内容验收

Pilot 至少覆盖：

- 手动成功；
- click/scripted autopilot；
- direct baseline；
- 超时或停滞；
- 人工急停；
- 人工接管；
- 至少一类恢复；
- 不同 route；
- 多个操作者或明确声明当前只有单操作者。

### 15.3 Gold 验收

- gold episode 复核覆盖率 100%；
- validation/test 双人复核或有等价仲裁流程；
- 人工示范与自动生成数据明确分层；
- 成功和失败定义固定；
- reward 可从状态与版本化公式重算；
- Safety Shield 介入可以单独统计；
- 数据卡完整；
- 不把小规模 pilot 称为生产级或临床级数据集。

## 16. 第一轮采集建议

下面是工程 pilot，而不是最终规模承诺：

| 批次 | 数据来源 | 目的 |
|---|---|---|
| P0 | 3～5 个 scripted/click autopilot episode | 验证 requested/effective action 记录 |
| P1 | 3～5 个手动正常 episode | 验证 HCI 时序、接管和 UI 事件 |
| P2 | 3～5 个超时/急停/失败 episode | 验证 termination 与危险片段 |
| P3 | 3～5 个预设错误状态恢复 episode | 验证 recovery 标签 |
| P4 | 少量策略 rollout + 人工纠正 | 验证 DAgger schema |

每完成一个批次就暂停，生成质量报告并修正采集器。不要等全部采完才发现动作标签错位。

## 18. 常见错误

### 18.1 只记录客户端 action

结果：autopilot 数据显示零动作，Safety Shield 修改也不可见。

修正：服务端同时记录 requested、controller 和 effective action。

### 18.2 只记录 `state_t`，不记录 `next_state`

结果：无法可靠构造 transition，容易产生一帧偏移。

修正：在一次 `step()` 的同一事务边界保存 state before、action 和 state after。

### 18.3 把每个危险 frame 当成一个危险事件

结果：一次持续 30 帧的接触被计为 30 次事故。

修正：同时保留 frame-level flag 和基于状态边沿合并后的 event-level 统计。

### 18.4 把 HCI 频率当成固定 60 Hz

结果：速度、动作持续时间和积分指标错误。

修正：记录真实 `dt`、单调时间、仿真时间和 action hold。

### 18.5 把 `guided` 数据混进 physics 数据

结果：策略学习到运动学中心线覆盖行为，评估却声称是 Newton 物理能力。

修正：`fidelity_mode` 是必填字段；高保真训练和测试只接受声明的 physics 数据。

### 18.6 只采集成功

结果：模型不会识别失败前兆，也不会恢复。

修正：按 collection card 主动采集失败、恢复和接管。

### 18.7 先按 route 随机切分

结果：同一患者几何泄漏到测试集。

修正：先按原始 case/patient 分组，再生成派生 route。

### 18.8 直接修改原始标签

结果：无法追踪谁修改了什么，也无法重建旧版本。

修正：原始数据不可变；标签修订进入 reviews/annotations 派生层。

### 18.9 把自动数据称为 gold

结果：数据质量声明与实际复核过程不一致。

修正：明确 raw/silver/gold 分级和人工复核覆盖率。

## 19. 推荐实施顺序

```text
D0  定义 schema、事件枚举和 collection card
 ↓
D1  把 recorder 接入服务端 step 边界
 ↓
D2  同时记录 requested / ShapeIntent / effective action
 ↓
D3  实现流式 shard、崩溃恢复和 checksum
 ↓
D4  完成 raw → episode → transition 构建器
 ↓
D5  完成自动质检、quarantine 和质量报告
 ↓
D6  完成人工复核界面与 gold 标注
 ↓
D7  按 case 分组并冻结 validation/test
 ↓
D8  发布 dataset manifest 与 data card
 ↓
D9  才开始 BC、DAgger 或离线 RL
```

最先要验证的不是“能否采集很多数据”，而是：

1. action 是否是物理引擎真正执行的 action；
2. transition 是否严格对齐；
3. episode 边界是否可靠；
4. 数据是否可追溯和重建；
5. 自动与人工数据是否明确区分；
6. 测试集是否真正隔离。

这些条件满足后，数据规模才有意义。
