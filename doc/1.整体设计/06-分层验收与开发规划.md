# 分层验收与开发规划

日期：2026-07-11

本文按 `doc/` 目录的五个职责层，对当前项目进行阶段验收，并给出下一步开发规划。验收依据来自：

- `doc/1.整体设计/01-总体技术方案.md`、`02-资产与数据规格.md`、`03-API与通信协议.md`、`04-部署与开发指南.md`、`05-开发进度记录.md`
- `doc/2.图像分割路径规划层/06-segment_part_graph规划方案.md`
- `doc/3.后端仿真层/*`
- `doc/4.前端层/*`
- `doc/5.训练层/*`

## 一、总体结论

当前项目已经形成“真实血管资产/中心线规划 -> 后端仿真与风险状态 -> WebSocket 状态批次 -> Godot 医疗导航前端”的主链路。VPP 路径规划、NavigationEngine 桥接、WebSocket 批次通信、B-spline 平滑、V-HACD/Newton 物理验证、Godot 前端基础工作站、路径线真实风险着色、路径驱动跟随相机与规划血管走廊可见性均已有落地记录。

但项目仍处于“演示链路可运行、训练闭环未完成、物理真实性持续增强”的阶段。最关键的下一步不是继续增加视觉效果，而是把各层验收标准收紧为可重复测试：路径规划资产质量、物理接触稳定性、导丝大曲率操作流程、HCI/RL 数据闭环、前端实机验收截图与回放。

## 二、1.整体设计层

### 2.1 职责范围

整体设计层负责项目边界、分层架构、资产规格、API 协议、部署方式、开发进度和跨层验收口径，是所有分层工作的唯一归档入口。

### 2.2 当前验收情况

已完成：

- 总体技术方案已明确平台定位：介入导丝/导管仿真、路径规划、HCI/RL 一体化、医疗导航前端。
- 资产规格已覆盖 CathSim 原生资产、VPP 血管资产、segment_part 空腔体模、中心线图、动作空间和 WebSocket JSON 数据格式。
- API 协议已定义 `session_start`、`control`、`state_update`、`state_batch`、`path_request/path_response`、`shape_intent` 等关键消息。
- 部署指南已覆盖 Python 环境、Godot 客户端、微服务启动、Docker 部署、RL 训练入口。
- 开发进度记录已持续追踪到第 40 阶段，覆盖路径规划、仿真、前端渲染、风险着色与导航相机。

待补齐：

- 当前进度记录较长，阶段条目多，缺少一份可直接用于项目验收的“总验收矩阵”。
- 文档与代码之间仍有部分历史方案残留，如 guided/physics/newton_demo 的边界需要统一描述。
- Godot 实机验收与自动化测试之间尚未形成一一对应的证据链。

### 2.3 下一步开发规划

P0：

- 建立总验收矩阵：每个阶段对应“代码入口、数据来源、测试命令、实机验收截图/日志、未通过项”。
- 将 `state_batch` 最新字段作为协议基线，补充到 `03-API与通信协议.md`，避免前后端继续各自扩展。
- 将 `05-开发进度记录.md` 中已完成阶段提炼为短版里程碑索引，长记录保留为审计日志。

P1：

- 增加“模式语义”总表：`physics`、`guided`、`newton_demo`、`rl`、`manual`、`autopilot` 分别说明真实程度、适用场景和不可声称的能力。
- 建立实机验收模板，固定记录 Godot 版本、后端 commit、phantom、target、engine、测试步骤和截图。

## 三、2.图像分割路径规划层

### 3.1 职责范围

图像分割路径规划层负责血管中心线、拓扑图、分支端点、半径数据、A* 路径规划、路径平滑和图资产质量，向后端仿真层提供真实路径输入，向前端提供可视化和导航依据。

### 3.2 当前验收情况

已完成：

- `segment_part_graph规划方案` 已明确体素化、骨架提取、关键点识别、分支聚类、B 样条平滑、`graph.json` 生成和 NavigationEngine 集成路径。
- VPP 路径规划链路已在开发进度中记录为完成：图加载、A* 路径规划、路径长度、节点数、耗时输出。
- B-spline 平滑已贯通 REST/WebSocket，路径锯齿问题已有阶段验收记录。
- 路径半径数据已经成为后续 Newton 真实腔碰撞和前端规划血管走廊可见性的关键输入。

待补齐：

- `segment_part` 图连通性和分支质量仍需要持续校验，历史记录中曾指出复杂血管图规划不够稳固。
- 路径点、半径、目标端点、入口点之间缺少统一的资产质量报告。
- 部分路径规划资产仍缺少“可达性 + 半径覆盖 + 曲率分布 + 分支命名”的自动验收。

### 3.3 下一步开发规划

P0：

- 为每个 phantom 生成 `route_quality_report.json`：包含节点数、边数、连通分量、入口到目标可达性、路径长度、最大曲率、最小半径、半径缺失率。
- 对 `segment_part` 和 `aorta_tree` 做全目标 A* 扫描，列出不可达端点和断裂边。
- 确认 `path.vessel_radius` 的单位和来源，作为前端走廊显示、后端碰撞壁厚、风险评估的共享字段。

P1：

- 增加路径重采样统一工具，保证后端物理、前端相机、路径线渲染使用相同弧长参数化。
- 对大曲率路段自动打标签，为后端流程引导和训练 curriculum 提供输入，但不得直接伪造风险等级。

## 四、3.后端仿真层

### 4.1 职责范围

后端仿真层负责物理引擎抽象、NavigationEngine 状态提取、Newton/XPBD 可行性、导丝分段模型、同轴支撑系统、风险评估、ShapeIntent 控制落地和 WebSocket 服务端数据输出。

### 4.2 当前验收情况

已完成：

- 物理引擎抽象和实时性能架构已明确：先做 PhysicsEngine 抽象，再逐步推进实时链路和 Newton/Warp 可行性。
- Newton 独立版路线已被选为优先路径，D0-D3 阶段已有完成记录。
- aorta_tree Newton demo 已完成真实腔碰撞、最小阶段 D 驱动和远端上线验证，记录显示部分端点可达且无穿管。
- WebSocket `state_batch` 已输出导丝 bodies、路径、目标、风险、`guidewire_mechanics` 等前端所需字段。
- 风险状态已从真实 `risk_score`、`wall_distance`、`safety_status` 等后端字段映射，不再由前端凭颜色或曲率猜测。
- 大曲率转弯流程方案已拆为 tip shape、orientation、support、micro advance、wall-slide、strategy switch 六个临床步骤。

待补齐：

- 导丝分段连续体模型和同轴支撑系统仍主要处于方案阶段，尚未完全成为 NewtonEngine 的可配置器械模型。
- `lateral_force_n`、`axial_force_n`、`torque_nm` 当前没有真实来源，仍应保持 `None`，不能前端补假值。
- 大曲率过弯的流程引导尚未完整转化为后端状态机和可测试事件。
- 物理模式、guided 模式和 Newton demo 模式仍需在协议中明确保真度边界。

### 4.3 下一步开发规划

P0：

- 实现大曲率流程引导后端状态机：`tip_shape_state`、`orientation_score`、`support_state`、`micro_advance_state`、`wall_slide_state`、`strategy_switch_state`。
- 为 `state_batch` 增加流程引导字段，但所有字段必须说明真实来源；缺少真实传感/计算来源时输出 `null` 或 `unknown`。
- 完成导丝分段参数层的最小实现：tip 段、柔软段、过渡段、支撑段的长度、刚度、阻尼、可视标记。
- 建立大曲率过弯测试集：至少覆盖安全贴壁滑入、顶壁高风险、卡滞后退、策略切换四类场景。

P1：

- 将同轴支撑系统接入 NewtonEngine：sheath/catheter/microcatheter 的推进、回撤、支撑长度、自由段计算。
- 将真实横向力、轴向力、扭矩拆分纳入风险评估；没有拆分前继续保持 `None`。
- 固化远端部署脚本和版本自检，保证前端看到的 engine 与后端实际物理引擎一致。

## 五、4.前端层

### 5.1 职责范围

前端层负责 Godot 医疗导航工作站、DSA/3D 窗格、血管与导丝渲染、路径可视化、风险颜色、导航相机、HUD 指标、流程引导面板和用户交互。

### 5.2 当前验收情况

已完成：

- `11-前端设计方案` 已定义医疗工作站画布、顶部状态栏、DSA 区、3D 导航区、数据卡片、底部控制区、颜色和交互状态。
- 3D 血管导航渲染已完成多轮改造：GLB 血管、菲涅尔玻璃材质、发光路径、方向立方体、窗格互换、环绕相机、跟随按钮。
- 路径线安全颜色已改为真实后端 `guidewire_mechanics` / `risk_score` / `wall_distance` 驱动，缺失 mechanics 时显示 stale。
- 默认 FOLLOW 相机已接入真实路径切线，新增 `navigation_camera_controller.gd`，避免只跟导丝 `_dir` 导致大曲率侧切。
- FOLLOW 血管可见性已改为规划路径走廊优先，使用 `path.vessel_radius` 扩展走廊，避免“规划远端隐藏、无关分支保留”的反向策略。

待补齐：

- Godot CLI 当前环境不可用，GDScript 语法和实际渲染仍需要编辑器实机验收。
- 第一人称内窥镜视角的稳定 up、遮挡裁剪和流程语义尚未完全落地。
- DSA 叠加层仍主要是占位/模拟几何，未接入真实 2D 投影流。
- 大曲率流程引导 UI 方案已写入文档，但尚未完整实现为面板、状态卡、训练评分联动。

### 5.3 下一步开发规划

P0：

- 做 Godot 实机验收脚本化清单：默认 FOLLOW、大曲率转弯、路径线红黄白恢复、规划血管走廊、切分支后路径刷新。
- 实现大曲率流程引导最小前端面板：显示当前步骤、推荐操作、风险原因、策略切换建议。
- 将流程引导面板只绑定后端真实状态，不根据前端颜色或屏幕距离猜测。
- 修复历史注释和乱码文档片段，避免维护时误读旧策略。

P1：

- 完成第一人称内窥镜 V5：侧偏/前视、稳定 up、导丝近端裁剪、路径发丝线。
- 接入 DSA 真实投影数据契约：导丝、路径、目标、风险区域统一从后端投影或影像服务输出。
- 建立 Playwright/Godot 截图验收或人工截图归档流程，为视觉改动留下可复现证据。

## 六、5.训练层

### 6.1 职责范围

训练层负责 HCI/RL 一体化平台、ShapeIntent 控制抽象、RL 环境、观察/动作/奖励设计、训练管线、策略推理回灌 HCI 和训练评分。

### 6.2 当前验收情况

已完成：

- `ShapeIntent` 已被明确为控制抽象，不是物理力场；其职责是把用户或策略意图转换为后端可执行控制。
- HCI/RL 一体化设计已明确双模式共享核心：路径规划、NavigationEngine、风险评估、状态批次和前端显示共享。
- RL 环境设计已给出 observation、action、reward、reset 随机化、curriculum、Gymnasium 注册和训练入口。
- 平台文档已规划 HCI 模式 API、RL 模式 API、策略推理到 HCI 的加载流程和 Docker/GPU 自检。

待补齐：

- `NavigationGymEnv`、训练入口、策略保存/加载、HCI 推理回灌仍主要处于规划阶段。
- 训练评分尚未完整接入真实流程事件，如顶壁、卡滞、微推进、回退、策略切换、支撑建立。
- 保真度模式需要严格标注，避免用 guided 演示数据训练后声称具备完整物理真实性。

### 6.3 下一步开发规划

P0：

- 实现 `NavigationGymEnv` 骨架：复用 NavigationEngine，输出与 HCI 一致的 observation，action 采用 ShapeIntent。
- 建立最小 reward：路径进度、路径偏离、壁距风险、接触力、停滞惩罚、完成奖励。
- 训练数据记录器：保存状态批次、控制输入、风险事件、流程步骤、路径进度和 episode 结果。

P1：

- 训练 curriculum：从简单直段、单弯、大曲率、分支选择逐步提升。
- 支持策略推理回灌 HCI：`session_start` 指定策略后，由后端推理 ShapeIntent，再经 Controller 落为 push/rotate。
- 将大曲率流程引导事件作为训练评分与专家回放标签。

## 八、近期建议开发顺序

1. 先收口文档和协议：把 `state_batch` 最新字段、模式语义、验收矩阵写成项目基线。
2. 再做路径资产质量报告：确保规划路径、半径、分支和目标数据可靠。
3. 接着实现后端大曲率流程状态机：先输出真实状态，不急着做复杂 UI。
4. 前端接入流程引导面板和实机验收清单：显示真实状态，不做猜测。
5. 最后启动训练层最小 Gym 环境：复用相同状态字段，避免 HCI 与 RL 两套世界。

## 九、验收红线

- 不得把曲率、颜色、屏幕距离直接伪造成风险、力或扭矩。
- 不得在缺少真实数据时默认显示安全；缺数据必须显示 `unknown`、`stale` 或 `null`。
- 不得用旧路径、旧分支或旧 phantom 的缓存驱动相机、碰撞或风险判断。
- 不得把 guided 运动学演示结果写成完整物理仿真能力。
- 所有前端视觉判断必须能追溯到后端字段、资产文件或明确的 fallback 规则。
