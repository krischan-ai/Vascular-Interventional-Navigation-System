# 物理引擎抽象与实时性能架构

> 版本：v1.0 | 日期：2026-06-26
> 适用范围：aorta_trunk 物理模式实机卡顿问题定位、是否迁移物理引擎的决策、实时控制链路重构方案
> 关联文档：[01-总体技术方案](01-总体技术方案.md)、[03-API与通信协议](03-API与通信协议.md)、[05-开发进度记录](05-开发进度记录.md) §二十八

---

## 〇、本文要解决的两个问题

1. **现象**：Godot 切到「主动脉本干 Aorta-Trunk」物理模式后，导丝运动严重卡顿，但机器内存 / CPU / 显卡都没有打满。
2. **决策**：要不要为了性能把物理引擎从 MuJoCo 迁移到 Warp/XPBD 或 SOFA？

本文给出实测数据、根因、是否迁移的判断，以及推荐的架构演进路线。**结论先行**：

- 卡顿的根因是**单核串行物理的单步延迟**，不是资源容量不足；堆硬件（更多核 / 更大显存 / 更强 GPU）救不了单个交互式仿真。
- **现在不适合迁移物理引擎，适合做物理层抽象**。但抽象的首要收益不是「为将来换 Warp 铺路」，而是**立刻把现在硬编码在 `NavigationEngine` 里的 guided / physics 双引擎拆开**。
- 实时链路应从 lock-step 改为「物理线程自主步进 + 客户端插值」，但必须诚实认识到：**这买到的是观感流畅，不是控制手感**——物理仍是低频，控制延迟地板依然存在。

## 一、性能实测与根因

### 1.1 实测数据

诊断工具：`tools/measure_physics_reach.py`（构建 `NavigationEngine` 物理模式、预穿线、计时步进）。

测量对象：`aorta_trunk` phantom（520 块密封壁砖碰撞体 + 预穿线长导丝），与前端 `MODELS` 配置一致。

| 配置 | 步进速率 | 单步耗时 | 能否铺到目标 |
|------|---------|---------|-------------|
| n_bodies=130, n_substeps=2（**前端当前**） | ~1.5 step/s | ~650 ms | ✅ progress 1.0 |
| n_bodies=130, n_substeps=1 | ~3 step/s | ~350 ms | ✅ progress 1.0 |
| n_bodies=60, n_substeps=1 | **~25 step/s** | ~40 ms | ❌ 只到 0.489（125mm/256mm） |

reset 耗时（MJCF 编译 520 壁砖 + 预穿线 IK 落位）：约 **18–20s**。

### 1.2 根因：延迟受限，不是吞吐受限

**卡顿来自单步物理的串行延迟，而非资源耗尽。** 三种「算力充裕」恰好都帮不上这个单步：

1. **CPU 核多 = 吞吐高 ≠ 单步快。** MuJoCo 的 `mj_step`（碰撞检测 + 约束求解）是**单线程串行**，一步只跑在一个核上。把两个仿真并行跑，它们各占一核、互不加速，每个仍是自己的单步延迟。多核能让你**同时跑很多个**环境（RL 批量训练吃这个），但救不了**一个**交互仿真的延迟。
   → 这就是「CPU 没打满」的原因：例如 16 线程机器上一个核 100% ≈ 总占用 ~6%。

2. **显卡对这里的物理零贡献。** 项目锁定 `mujoco 2.3.7`（CPU 物理）。GPU 只被 Godot 客户端用于渲染，而渲染从不是瓶颈。唯一能上 GPU 的是 **MuJoCo MJX（JAX/XLA）**，但它的优势是**几千个并行环境**的批量推进；**单环境**逐步延迟因 kernel 启动开销往往**比 CPU 还慢**，且与当前 2.3.7 / dm-control 1.0.14 栈不兼容。

3. **真正的杠杆是模型 DOF，且是超线性的。** 见 1.1 表：壁砖数恒为 520，仅把 n_bodies 130→60 就从 3 step/s 飙到 25 step/s（**~8x，而体数只降 2.2x**）。约束求解对接触 / 自由度超线性——**导丝节数是主成本，不是壁砖数**。慢是算法复杂度造成的，砸硬件买不回来。

### 1.3 死结：节数与到达性绑定

130 节不是随便定的。导丝段长由其**物理直径**决定（[src/cathsim/dm/components/guidewire.py](../src/cathsim/dm/components/guidewire.py) `get_body_properties`：`offset = sphere_radius + cylinder_height*2`，约 **2mm/节**）。要让预穿线导丝铺满 256mm 管腔到达目标，就得 ~130 节。

- 降到 60 节：速度上天（25 step/s），但导丝只有 ~125mm 长，**够不到目标**（progress 0.489）。
- 想又快又够长又不失真：**做不到**——除非把导丝做粗（不物理）。

**结论：要用物理尺寸的铰接导丝铺满 256mm 管腔，就内在是 ~1.5–3 Hz。这是一个硬地板，任何架构改动都抬不动它。**

## 二、是否迁移物理引擎的决策

### 2.1 判断：现在不迁移，做抽象

| 维度 | 判断 |
|------|------|
| 战略（别迁移 / 先抽象 / Strangler 渐进替换） | ✅ 正确，是核心价值 |
| 「卡顿主要是架构不是物理」 | ⚠️ 半对：解决观感，解决不了低频控制延迟地板 |
| 「去锁步控制就不卡」 | ❌ 过度推销：插值换的是平滑，不是手感 |
| 物理层耦合深度 | ⚠️ 实际比直觉深，`NavigationEngine` 本身约一半是 MuJoCo 内脏 |

**为什么不迁移：**

1. **迁到 Warp/XPBD 不是「换引擎」，是从零写导丝连续体 solver**（stretch / bend / twist / self-contact + 接触）。这正是 MuJoCo 白送的部分，工作量极大。
2. **当前定位到的问题（B样条路径不显示、卡顿、锁步刷新）90% 不在 MuJoCo**，换引擎这些问题照旧。
3. **上层算法（NavigationState / Control / Planner / Risk / 未来 RL / 回放）尚未冻结**，此刻换状态结构 = 全部重新验证，成本高。

### 2.2 对「卡顿是架构问题」论点的修正

这个论点**只对了一半**：

- 对**视觉流畅**——对，架构（解耦 + 插值）能解决。
- 对**控制手感**——错。本平台按总体技术方案要做**介入训练**，训练在意操作延迟 / 力反馈手感，不只是画面帧率。1.3 的 ~3Hz 物理 = **~333ms 控制延迟**，对「练手法」不合格，无论插值后画面多顺。

**插值是创可贴，不是解药。** 自相矛盾之处在于：恰恰是这个 3Hz 延迟地板，才是将来真要做物理训练手感时迁移到 GPU solver（单根连续体可上 60Hz+）的**唯一正当理由**——而判据是「训练手感」，不是「画面流畅」（后者插值已够）。

### 2.3 对「物理层已基本解耦」的修正

乐观了。真正依赖 MuJoCo 的不止 `reset/step/physics`：

- **预穿线 IK**（`NavigationEngine._thread_physics_along_path`）直接读关节轴、qpos 索引、body 树。
- `insertion_max` / `stiffness_scale` 是 MuJoCo 关节语义。
- prethread 落位靠 FK 自洽校验。

这些**塞不进**干净的 `step/reset/get_state` 接口，会从抽象层漏出。**`NavigationEngine` 本身就是最难抽的硬骨头，内部约一半是 MuJoCo 专有逻辑**，真实可复用率没有「90%」。

## 三、物理引擎抽象（PhysicsEngine 接口）

### 3.1 抽象层的首要收益（被普遍低估的那条）

通常把 PhysicsEngine 抽象的收益挂在「将来换 Warp」上，于是显得超前。但有一条**立刻兑现**的收益：

**`NavigationEngine` 现在自己就同时塞了两个引擎。** `step()` / `reset()` / `get_render_bodies()` 里到处是：

```python
if self._is_guided():
    ...  # 运动学：沿中心线按弧长合成导丝点位，不读物理
else:
    ...  # MuJoCo 物理：env.step / 提取物理几何
```

这本身是耦合异味。PhysicsEngine 接口的**第一收益不是 Warp，而是把 guided 拆成 `KinematicEngine`、把 MuJoCo 拆成 `MuJoCoEngine`**，让 `NavigationEngine` 不再 if/else 二选一。这个收益今天就能拿到，且与迁移无关——**这才是「立即做」最硬的论据**。

### 3.2 接口草案

```python
class PhysicsEngine(Protocol):
    def reset(self) -> NavigationState: ...
    def step(self, delta_push: float, delta_rotate: float) -> NavigationState: ...
    def get_render_bodies(self) -> list[dict]: ...   # 每节 body 的 pos（+ 可选 quat）
    def get_tip(self) -> TipPose: ...
    def close(self) -> None: ...

    @property
    def planned_path(self) -> list[list[float]]: ...
```

实现：

```
            FastAPI / WebSocket
                    │
              NavigationEngine     ← 编排：状态规范化、路径进度、风险、autopilot
                    │
            PhysicsEngine（接口）   ← 新增抽象层
          ┌─────────┴─────────┐
   KinematicEngine        MuJoCoEngine        （未来：WarpEngine）
   （guided 运动学循线）   （make_dm_env 物理）
          │                    │
     中心线弧长插值          MuJoCo 2.3.7
```

**原则：MuJoCo 专有逻辑（prethread IK / insertion_max / stiffness_scale / 关节布局）显式归 `MuJoCoEngine` 内部，不假装通用。** 抽象接口只暴露 step/reset/state/render_bodies/tip 这些跨引擎稳定的概念。

## 四、实时控制链路重构

### 四个改动是一个整体，不是四个独立优先级

当前链路是 **lock-step（锁步）**：

```
Godot 发 control → 等 → FastAPI step() → MuJoCo → state_batch → Godot 绘制 → 再发下一个 control
=> Godot 刷新率 = MuJoCo 步进率
```

目标链路：

```
            Godot（60fps 渲染线程，对 body 位姿做插值）
                ▲ 双缓冲 State Buffer
        WebSocket 主动推送（20–30Hz）
                ▲
        Physics Worker（持续 step，读最新输入）
                ▲ 最新输入缓存（Input Buffer）
            Godot 控制输入（按住即更新 latest_input）
```

四个改动**必须一起做**：

| 改动 | 作用 | 关键约束 |
|------|------|---------|
| ① 物理线程自主连续步进 | 物理不再等 control 才走一步 | 见下「易踩的坑」 |
| ② 输入缓存（latest input） | 物理每步读最新输入，不一帧一请求 | **必须和①同时做** |
| ③ WebSocket 改主动推送 | 物理→客户端单向流，不走请求/响应 | 20–30Hz 即可 |
| ④ 客户端导丝插值 | 在两帧物理位姿间 Lerp/Slerp，60fps 滑过 | 见下「插值范围」 |

### 易踩的坑（来自现有代码的设计意图）

1. **lock-step 不是 bug，是有意为之。** [godot_client/scripts/websocket_client.gd](../godot_client/scripts/websocket_client.gd) 的 `_awaiting` 锁步注释明确：防止前端以 60fps 灌满后端导致心跳饿死、延迟暴涨。**只做①去锁步、不做②输入缓存 = 队列瞬间堆积、延迟爆炸，比现在更糟。** 二者是同一改动的两半。

2. **`run_in_executor` 已经是并发的，不是同步的。** [services/websocket_handler.py](../services/websocket_handler.py) 的 `_run_blocking` 跑在线程池里，而 `mj_step` 会**释放 GIL**，所以它已和事件循环并发（阶段九加它正是为「避免阻塞事件循环、根治 pong 超时」）。它缺的不是「异步性」，而是「**自主连续步进**」——现在只在收到 control 时步一下。

3. **插值要插「所有 body」，不只是 tip。** 导丝是整条管子，需对 130 节 position 做 Lerp、（若有 quat）做 Slerp，再重建 tube。只插 tip 会导致管身撕裂。

4. **「每帧重建 Mesh」只有在做了插值之后才是问题。** 当前 [godot_client/scripts/guidewire_renderer.gd](../godot_client/scripts/guidewire_renderer.gd) 用 `ImmediateMesh`，130 体 ×8 边 ×6 顶点 ≈ 6千顶点/次，在 1.5–3Hz 下成本可忽略；变成 60fps 重建后才需关注（届时可考虑 `ArrayMesh` 顶点更新 / 减少 `wire_sides`）。**别在插值之前就提前优化它。**

5. **物理 body 数不能按相机距离做 LOD。** body 数在 reset 时固定、决定到达性，不能中途改。可以做的是**渲染端按距离抽稀折线**（远处少画几段），物理 LOD 不成立。

### 必须诚实标注的代价

- 插值要**落后**最新物理帧约一帧来做平滑 → **控制延迟不降反略升**。
- 它解决的是**观感（视觉 jank）**，不是**手感（控制响应）**。物理仍是 ~3Hz。
- 建议在前端 HUD 显式标注「**演示 / 物理**」模式，避免让人误以为这是可训练手感的保真物理。

## 五、附：Issue #1 修复记录（B样条路径切换后不显示）

**现象**：Godot 启动模型能看到 B样条规划路径；M 键切到 aorta_trunk（或任何其它模型）后路径消失。

**根因**：`planned_path`（aorta_trunk 为 132 个 B样条点）只在每个会话首帧 batch 下发一次，由 `ConnectionState.path_sent` 标志控制。但 `path_sent` 是**连接级**标志，下发后置 `True`，而 [services/websocket_handler.py](../services/websocket_handler.py) 的 `_handle_session_start` **从不复位它**。M 键切换走 `restart_session`——复用同一条 WebSocket 连接、同一个 `ConnectionState`，只发 `session_stop` + `session_start`，于是新会话首帧 `include_path = not path_sent = False`，新模型路径永不下发（按 R 重置才会强发，因 `_handle_reset` 无视该标志）。

**修复**：在 `_handle_session_start` 设置 `session_id` / `batch_mode` 后复位 `conn_state.path_sent = False`，使每个新会话重新下发自身路径。

> 注意：物理模式 step 仅在收到 control 时发生，故切完模型需先推一下导丝才会收到首帧 batch、路径才出现。与其它模型行为一致。

## 七、实施方案规划（分阶段、可回滚）

本节把第六节的「立即做」拆成可执行、可验收、可独立回滚的阶段。每阶段都遵守一条铁律：**上层契约（`NavigationState` 字段、`state_batch` 协议、Godot 渲染输入）保持不变**，只在其下做替换。这样任一阶段失败都能单独回退，不波及前端与算法。

### 阶段 A：PhysicsEngine 抽象 + 拆双引擎（纯后端、零协议变更）

**动机**：消除 `NavigationEngine` 里 guided / physics 的 if-else 双引擎异味；为后续实时改造和远期迁移提供稳定接缝。**不为 Warp，先为可读 / 可测。**

**现状接缝**（已核对）：
- `services/session_manager.py:133` 是唯一的引擎构造点：`NavigationEngine(**engine_kwargs)`。
- `NavigationEngine.step` / `reset` / `get_render_bodies` / `_extract_state` 内部按 `_is_guided()` 分叉（[services/navigation_engine.py](../services/navigation_engine.py)）。
- guided 专有状态：`_s` / `_path_total_len` / `_advance_per_step` / `_guided_state()` / `_guided_render_bodies()`。
- physics 专有状态：`_env` / `_time_step` / 预穿线 IK / `insertion_max` / `stiffness_scale`。

**目标结构**：

```
services/
  physics/
    __init__.py
    base.py          # PhysicsEngine 协议 + 共享 NavigationState 规范化
    mujoco_engine.py  # make_dm_env + 预穿线 IK + insertion_max/stiffness_scale
    kinematic_engine.py  # 沿中心线弧长推进（原 _guided_* 逻辑迁入）
  navigation_engine.py  # 瘦身为编排：选引擎、算 path_progress/deviation、风险、autopilot
```

**接口（最小稳定集，跨引擎概念）**：

```python
class PhysicsEngine(Protocol):
    def reset(self) -> RawPose: ...                 # tip + 每节 body 原始位姿
    def step(self, push: float, rotate: float) -> RawPose: ...
    def render_bodies(self) -> list[BodyPose]: ...  # 给前端的 body 列表
    def close(self) -> None: ...
    @property
    def planned_path(self) -> list[list[float]]: ...
```

**关键约束**：
- `RawPose` 只含跨引擎稳定量（tip position/direction/quaternion、body 位姿、接触力）。**派生量（path_progress / path_deviation / wall_distance / curvature / safety / risk）留在 `NavigationEngine`**，因为它们与引擎无关、且被上层算法依赖——绝不能下沉到引擎实现里，否则每换一次引擎都要重写。
- MuJoCo 专有参数（`insertion_max` / `stiffness_scale` / `prethread` / 关节布局）**只出现在 `MuJoCoEngine.__init__`**，不进 `PhysicsEngine` 协议。`NavigationEngine` 通过工厂按 phantom 决定传哪些。
- guided 与 physics 不再共存于一个对象：`NavigationEngine` 持有**一个** `self._engine: PhysicsEngine`，由工厂在构造期二选一（`KinematicEngine` 或 `MuJoCoEngine`）。`_is_guided()` 退化为 `isinstance(self._engine, KinematicEngine)`，最终删除分叉。

**迁移步骤（保持绿测）**：
1. 抽 `base.py`：定义协议 + 把 `_extract_state` 中**引擎无关**的派生计算留在 `NavigationEngine`，把**引擎相关**的原始读取抽成 `RawPose`。
2. 把 `_env` / `_time_step` / 预穿线 IK 整体搬进 `MuJoCoEngine`，`step/reset` 委托。
3. 把 `_s` / `_guided_state` / `_guided_render_bodies` 整体搬进 `KinematicEngine`。
4. `NavigationEngine.__init__` 改为调工厂 `make_engine(phantom, guided, **kwargs) -> PhysicsEngine`。
5. 删 `_is_guided()` 分叉，`step/reset/get_render_bodies` 直接委托 `self._engine`。

**验收**：
- 现有套件全绿（websocket / api / nav / autopilot，约 53 passed），**无新增、无修改测试期望**——证明上层契约未变。
- 新增 `tests/test_physics_engine.py`：用一个 `FakeEngine`（返回脚本化 RawPose）驱动 `NavigationEngine`，**脱离 MuJoCo** 测 path_progress / risk 计算——这是抽象立刻兑现的可测性收益。
- `measure_physics_reach.py` 对 aorta_trunk 数值不变（progress 1.0 / dev 几 mm）。

**回滚**：阶段 A 是纯重构，git revert 即可；不触碰协议与前端。

### 阶段 B：实时链路重构（后端物理线程 + 前端插值，协议小幅扩展）

> 前置：阶段 A 完成（`PhysicsEngine` 就位，物理线程只需驱动 `engine.step`）。
> ①②③④ 是**一个原子改动**，分步实现但**必须一起上线**（见第四节「易踩的坑」）。

#### B.1 后端：PhysicsWorker 自主步进 + 输入缓存

```
services/realtime/physics_worker.py（新增）
```

- 每个 batch_mode 会话起一个 `PhysicsWorker`（线程或 `asyncio.to_thread` 持续循环），`while running: engine.step(latest_input)`。
- `latest_input`：双字段（push / rotate）原子覆盖；`control` 消息只更新它，**不再触发一次 step**。这同时根除「60fps 灌满后端」的队列堆积（替代现有 `_awaiting` 锁步）。
- 推送：worker 每步把最新 `RawPose` 写入会话的双缓冲 `StateBuffer`；一个 20–30Hz 的发送协程从 buffer 取最新状态 `state_batch` 推给客户端（**主动推送，不等 control**）。
- `path` 仍只首帧带（沿用 `path_sent`，见第五节修复）。

#### B.2 协议扩展（向后兼容）

- `control`：语义从「请求一步」变为「更新输入」，**报文格式不变**（仍 `delta_push` / `delta_rotate`）。旧客户端行为退化为「每发一次刷新一次输入」，可用。
- `state_batch`：新增可选 `seq`（物理帧序号）与 `t_phys`（物理时间戳），供客户端插值对齐。缺省字段不破坏旧客户端。

#### B.3 前端：导丝 body 插值

- [godot_client/scripts/websocket_client.gd](../godot_client/scripts/websocket_client.gd)：删 `_awaiting` 锁步；`control` 在 `_process` 里按需发送最新输入（按住即持续更新，不等响应）。保留 `session_id` 守卫与 4MB 入站缓冲。
- [godot_client/scripts/guidewire_renderer.gd](../godot_client/scripts/guidewire_renderer.gd)：缓存**上一帧 / 当前帧**的 body 位姿数组；`_process(delta)` 按到帧间隔时间求插值系数 `alpha`，对每节 position 做 `lerp`、（若有 quaternion）做 `slerp`，再重建 tube。tip 同理。
- 渲染 60fps，物理 ~3Hz，视觉平滑。

#### B.4 必须诚实标注的代价（写进 HUD）

- 插值落后最新物理帧约一帧 → 控制延迟不降反略升；解决的是观感不是手感。
- HUD 显式标「物理模式 / 演示模式」，并可选显示物理帧率（如 `phys 3Hz`）。

**验收**：
- aorta_trunk 物理模式：Godot 稳定 60fps，导丝**视觉无跳变**；松手后导丝停在最后物理位姿不抖。
- 后端：`control` 高频发送不再造成延迟累积（对比改造前的队列堆积）。
- 回归：guided 模型（segment_part / VPP）行为不变（它们也走 worker，但 `KinematicEngine.step` 廉价、可高频）。
- 心跳：高频输入下 ping/pong 不超时（worker 在独立线程，事件循环不被占用）。

**回滚**：协议为向后兼容扩展；前端可用 feature flag 切回锁步路径；后端 worker 可降级为「收到 control 才 step」的旧行为。

### 阶段 C：低风险性能微调（可并入 A/B，独立可回滚）

| 项 | 改动 | 预期 | 风险 |
|----|------|------|------|
| n_substeps=1 | [godot_client/scripts/main_controller.gd](../godot_client/scripts/main_controller.gd) aorta_trunk 条目 `n_substeps:1`，经 `_push_nav_config` 透传 | 物理 1.5→3Hz | 极低（实测 progress 仍 1.0） |
| 渲染 LOD | guidewire / path tube 远距离减 `wire_sides`、抽稀折线 | 远视角省顶点 | 低（纯渲染） |

> 注意：n_substeps 当前**未**经 per-model 透传——`main_controller._push_nav_config` 只推 guided / n_bodies / prethread / insertion_max。需补一条 `n_substeps` 透传（[websocket_client.gd](../godot_client/scripts/websocket_client.gd) 默认 2，`MODELS` 条目可覆盖）。

### 阶段 D：Warp/XPBD 可行性 demo（独立仓 / 独立分支，不接主线）

**唯一目的**：回答「单根连续体导丝在 GPU XPBD 上能否稳定 60Hz、且密封管腔接触不穿透」。

- 完全独立，不依赖也不修改主项目；输入用同一条带半径中心线（`data/aorta_centerline/`）。
- **判据是控制手感（60Hz 实时 + 接触稳定），不是画面流畅**——后者主线插值已解决。
- 仅当 demo 证明「GPU solver 能把 3Hz 地板抬到交互级手感」时，才进入「实现 `WarpEngine`（满足阶段 A 的 `PhysicsEngine` 协议）→ 灰度替换」的远期路径。届时 Godot / FastAPI / WebSocket / PathPlanner / RiskAssessor / `NavigationEngine` 编排层**均不需重写**——这正是阶段 A 抽象的兑现点。

### 依赖关系与里程碑

```
A（抽象拆引擎）──┬─→ B（实时链路：物理线程+插值）──→ 观感流畅达标
                 │
                 └─→ D（Warp demo，独立）──→ 决定是否远期迁移（判据=手感）
C（参数微调）：可随时并入，独立回滚
```

| 里程碑 | 标志 | 对应阶段 |
|--------|------|---------|
| M1 双引擎拆分 | `_is_guided` 分叉删除、可脱 MuJoCo 单测 | A |
| M2 视觉流畅 | aorta_trunk 60fps 无跳变、HUD 标注模式 | B + C |
| M3 手感判据 | Warp demo 给出 60Hz 单连续体可行性结论 | D |
| M4 远期迁移（条件触发） | `WarpEngine` 实现协议、灰度替换、上层零改 | A 的兑现 |

**不变量贯穿全程**：`NavigationState` 字段、`state_batch` 协议、Godot 渲染契约。任何阶段都不得为了性能破坏它们——否则上层算法（路径进度 / 风险 / 未来 RL / 回放）全部重新验证，得不偿失。
